## Decision

W1-002 is Accepted for the local/fixture boundary.

The implementation replaces per-bar D1 persistence with page/batch-oriented set-based SQL using bounded JSON payloads and `json_each(?)`, while preserving the existing Market Bar acceptance semantics.

Accepted evidence reported by Local and verified against the synchronized branch:

```text

```

Verified semantics:

- input result order is preserved;
- 100 normalized bars can be persisted in 7 D1 statements in the integration fixture;
- `INSERTED`, `MATCHED`, `CONFLICT`, `REJECTED` remain distinct;
- exact receipt replay remains idempotent and does not append new durable writes;
- a different receipt for the same canonical bar remains `MATCHED`;
- conflicting semantic content records conflict evidence and does not overwrite the canonical bar;
- an idempotency key reused for a different observation fails closed.

## Boundary

This acceptance removes the original W1-001 Stage-B blocker that Market Bar persistence required hundreds of D1 statements for a 100-bar page.

It does **not** by itself accept W1-001 Stage B because Worker-level combined D1 accounting is not yet wired end-to-end. The synchronized `worker.ts` still reports:


## Daily-write observation

The 100-bar initial fixture produces approximately 300 D1 row-write operations and a different-receipt MATCHED replay approximately 200. This is not a W1-002 rejection condition because W1-002 targeted per-invocation query compression without weakening Market acceptance guarantees.

However, W1-001 Stage-B Canary preflight must project daily row writes for the actual bounded scheduler workload before live activation. Do not infer Free-tier daily safety from the 7-query result alone.
